## 1. The finding: the archive stopped taking writes, twice, in silence

The health checks all watch what the site *serves*. Nothing watched what it
*keeps*. Reading the newest `<news:publication_date>` in the news sitemap —
that date is the archive's `first_seen_at`, so it dates the last successful
database write — and confirming against `/api/stats/archive-sources`:

| day | last archive row | dry for | news-sitemap |
|---|---|---|---|
| 2026-08-26 | `07:31:39Z` | **14 h** | 643 -> **132** entries, newest 14.4 h old |
| 2026-08-27 | `07:00:30Z` | **10 h** (when found) | 254 -> 228 entries, newest 10.4 h old |

Both days have the same shape: a cluster of bursts between 03:00 and 07:00
UTC (Aug 27: `03h:693 04h:26 05h:16 06h:18 07h:10` rows), then nothing.

Every existing probe was green throughout: all URLs 200, the dataset
regenerating every ~15 minutes, the news sitemap above its 50-entry floor,
the 30-minute uptime probe passing.

**What each stalled hour costs.** A story with no archive row has no
permanent home: when it ages out of the 72 h live dataset its URL answers
the deliberate retriable 500 and is eventually tombstoned to a 404. It also
never enters `/news-sitemap.xml` (gated on archive standing) and is never
pinged to IndexNow (pings only happen inside a burst). This is the exact
mechanism that permanently lost 205 stories in the 2026-08-20 outage and
cost 77% of impressions.

**Measured damage, not estimated:** the survival probe found **4 story URLs
answering 500 that were never archived** — still 500 after the catch-up
burst, and no longer advertised in either sitemap (`c7d3ec04f1ec2`,
`c0ccd6ae7e504`, `ca3c838eca4b0`, `c18da82be9726`). They are deliberately
NOT being tombstoned today: the probe's own 3-day rule exists so a revived
cluster is never written off early.

## 2. Root cause, in three layers

**Layer 1 — the gate was skipped.** `app/api/cron/news-refresh/route.ts`
returned EARLY whenever the dataset was younger than `RSS_REFRESH_MINUTES`,
so `shouldPersistNow()` was only ever consulted on ticks that also
refreshed.

**Layer 2 — the window was narrower than the beat.**
`lib/database/persist-gate.ts` opened the gate, on a cold instance, only in
minutes 0-4 and 30-34. A 5-minute window is guaranteed to catch a scheduler
only when its beat is <= 5 minutes.

Neither rule is wrong alone. Together they made the burst a coincidence
between a drifting phase and a narrow window. Fixing both restored writes —
530 rows in the 17:00 hour — **and then writes stopped again at 17:43**,
which is how the real cause surfaced:

**Layer 3 — nothing was calling the endpoint.** `vercel.json` carried a
single daily `0 6 * * *` cron, a Hobby-plan artifact (that tier allows one
daily cron); the 5-minute beat the code is written around came from an
EXTERNAL scheduler, and that scheduler is no longer reaching production.
Measured directly:

```
18:23:52  dataset generated
18:48:53  dataset still 18:23:52 — 25 minutes, against RSS_REFRESH_MINUTES=15
          archive rows since 17:44: 0
          stories in /rss with no archive row: 11 of 50
```

With no beat at all, the burst could only fire when traffic happened to
regenerate the cache inside the persist window. That is the whole 03:00-07:00
pattern: a wandering coincidence, twice observed, never a schedule.

## 3. Shipped — `e1b4cfb`, `ab2ac21` and `c88e8ab`, verified live

**The fix.** The cadence guard now skips the REFRESH only, never the burst.
The cold window is caller-aware: the **cron** gets half the cycle (any beat
of 15 minutes or less must land in one — proved exhaustively in
`persist-gate.test.ts` for every beat 1-15 and every phase 0-59), while the
**producer** keeps minutes 0-4/30-34, because it runs on cache-missing
traffic rather than on a beat. That split was not theoretical: the first
hour with the wide window applied to both showed writes in **12 distinct
minutes between 17:30 and 17:43**, which keeps Neon compute awake instead of
letting it suspend, so `ab2ac21` put the producer back on the narrow window
the same day.

**The scheduler.** `vercel.json` now runs `/api/cron/news-refresh` on
`0,15,30,45 * * * *`. Quarter-hourly matches `RSS_REFRESH_MINUTES`, so every
tick refreshes, and ticks land on minutes 0 and 30 — both inside the cron
cold window — so the burst runs ~2x/hour as the batching intends. That is
**96 invocations/day against the 288/day** a 5-minute beat implies, so it
sits below the cost the code was already written for. The sub-daily schedule
is possible because the account has been on Pro since 2026-08-24; the deploy
was watched to `success` to confirm the plan accepted it. If the external
scheduler ever returns, nothing changes: the cadence guard skips a refresh
younger than the interval and the persist gate batches the writes.

## 4. The url-survival gate was red for the site behaving correctly

`[auto-alert]` #4 said the "published URLs never 404" guarantee was broken,
212 times over. It was not: every one of those URLs is a tombstone this loop
placed deliberately on 2026-08-25 to stop those stories serving a
crawl-poisoning 500. A gate that is red every night for correct behaviour is
the same defect the GONE/LOST split was written to prevent, arriving from a
third side — and it buries the next real 404 among 212 expected ones.

`classifyResults()` now has a **TOMBSTONED** class: a 4xx whose cluster id is
listed in `data/lost-stories.json` is reported and does not fail the build.
Any other 4xx still fails. A 5xx on a tombstoned id is still an outage.
Tombstones are excluded from `RUN_HEALTHY_SHARE` entirely, so a growing list
can never quietly suspend LOST classification for unrelated 5xx. Six new
unit tests, one of which asserts a non-tombstoned 404 still fails alongside
a tombstoned one.

**Proven in CI, not just locally:** the 17:39 UTC `url-survival.yml` run —
the first to exercise the fix — is `success`, and the workflow closed issue
**#4** on recovery.

## 6. Two smaller monitoring defects, both fixed

- **`seo-health.yml` opened alerts and never closed them.** Its own run
  passed at 17:54 UTC today while issue #5 stayed open, so "an open
  auto-alert means broken right now" was simply false. It now closes the
  issue on a green run, like the other three probes already did.
- **A cross-id redirect in the news sitemap is usually a merge catching up,
  not a regression.** Restoring the write burst exposed it: a cluster
  archived at 17:30 was merged at 17:33 and stayed advertised until the
  archive-standing query's cache caught up — **9 of the first 400 entries at
  17:45, 0 two minutes later**. `seo-health.mjs` now does two things before
  believing such a failure. It re-checks once after 90 s against a fresh
  sitemap (an entry no longer advertised, or now answering 200, was a race).
  What survives that gets *looked up* rather than guessed at: the check asks
  `/api/stats/archive-sources` whether the source cluster is actually
  `merged`. It usually is — the gate reads archive standing through a
  30-minute cached query (`FIRST_SEEN_TTL_S`), so a story merged after that
  cache was populated stays advertised until it expires. Merged is a named
  note; **not** merged, or more than ten at once, still fails, because that
  would mean the gate itself is broken. Verified: a run that had been
  failing on one such URL now reports `SEO health: ALL CHECKS PASSED`.
