## Methodology caveat (new, worth keeping)

This cloud session's outbound HTTPS is TLS-intercepted by an Anthropic
egress proxy that re-signs every connection with its own CA and its own
(sliding, "now + 30 days") validity window — confirmed by probing unrelated
domains and seeing the same pattern. That means **certificate issuer and
date fields read via `curl`/`openssl` in a cloud run are not evidence about
the real origin's certificate** — only the CN/SAN (which the proxy sets
from the real upstream's SNI-matched identity) and HTTP-layer status codes
obtained via Node's native `fetch` (which this repo's own
`seo-health-static.mjs` already uses) are trustworthy signals in this
environment. Recorded as a MEMORY note so future runs don't misread raw
`curl -v` cert metadata as ground truth about GitHub's cert state.
