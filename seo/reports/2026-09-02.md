## 5. Fixed: two story URLs had been serving 500s for twelve days

`[auto-alert]` #6 has been red since 2026-08-29 and yesterday's run triaged it
as "not an active regression". Re-reading it against `data/url-ledger.json`
showed that was half right. Today's numbers (probe of 2026-09-01 11:43 UTC,
7,252 URLs): `GONE=0 UNAVAILABLE=1 LOST=2 TOMBSTONED=212`.

The 212 tombstones are by design. The **1 UNAVAILABLE**
(`…-c09b64edf8f88`) is genuinely transient — the ledger shows
`lastOk: 2026-09-01T11:43:09.260Z`, i.e. it answered 200 during that very run;
a `TypeError: fetch failed`, not a 500. It must **not** be tombstoned.

The **2 LOST** were real damage nobody had acted on:

```
ccddfbfe6be27  firstSeen 2026-08-20T21:53:36.200Z   lastOk: null
cf6482c8299dc  firstSeen 2026-08-20T22:18:06.000Z   lastOk: null
```

`lastOk: null` — they have **never once served a 200**, in twelve days, and
both were first seen inside the Neon egress outage window. That is precisely
the profile the 2026-08-25 tombstoning was built for, and they were missed for
a sharp reason: that extraction filtered on `lastOk < "2026-08-22"`, and in
JavaScript **`null < "2026-08-22"` is `false`** — so the URLs that never worked
at all, the most certainly-dead cases, were exactly the ones the filter skipped.

Both are now in `data/lost-stories.json` (205 → 207 ids), so they will answer a
clean 404 instead of a crawl-poisoning 500, and `url-survival.yml` should go
green — restoring a gate that had been permanently red and therefore
meaningless. **Like everything else today this is merged, not live**: it takes a
deploy (item 00), because `lost-stories.json` is compiled into the bundle.
Guarded by a new case in `tests/unit/archive-outage.test.ts` that also pins the
UNAVAILABLE id as *not* tombstoned, so a future sweep cannot 404 live content.

## 6. Merged (not live): the placeholder every image shipped and one image showed

The strategy queue's item 1 is LCP 6.0 s → under 2.5 s, and backlog item 3 said
the target is main-thread cost with no named cause. Splitting the homepage
document found one.

**62% of the homepage HTML (213,382 of 343,323 bytes) is the RSC flight
payload**, not markup — the serialized React tree Next embeds and parses on the
main thread during hydration. Its key census pointed straight at the defect:
112 `stroke`, 84 `x1`/`y1`/`x2`/`y2`, 29 `cx`/`cy`.

`RemoteImage` is a Client Component, and **every prop a Server Component hands
to a Client Component is serialized into that payload, rendered or not**.
`StoryImage` was passing `fallback={<CategoryPlaceholder …/>}` — a ~1,045-byte
SVG element tree per image, to display only if that publisher's CDN had killed
the asset. Measured live, escaped fingerprint (in the payload) vs unescaped
(in the markup):

```
/                                28 serialized,  1 shown
/top-100                         25 serialized,  0 shown
/most-covered                    25 serialized,  0 shown
/topic/artificial-intelligence   31 serialized, 17 shown
/politics /technology /us         4 serialized,  0 shown  (each)
                  120.4 KB of 1,833 KB across nine pages = 6.6% of bytes
```

`RemoteImage` now takes the resolved category **label** (~26 bytes). Passing the
`CategoryId` instead would have dragged `config/categories.ts` — 26 KB of
classifier keyword dictionaries — into the browser bundle and lost more than it
saved, so the label is resolved server-side deliberately.

**Guarded twice, and the second guard is the point.** The natural e2e payload
assertion passes for the wrong reason: with no news API key the dev server
Playwright drives serves fixture stories whose art is all *local* placeholder
SVG, so `RemoteImage` never renders in CI. `tests/unit/story-image-flight-payload.test.ts`
drives the remote branch directly and fails naming the offending prop — proved
by reintroducing the defect and watching it fail, then reverting.

**Honest scope:** ~25 KB off a 343 KB page does not move a 9.7 s
`domInteractive`. This is a contribution to the LCP work, not a solution, and
it is **not live** until deploys work.

## 8. Found chasing item 00: the weekly GSC data never reaches production

Checking whether today's tombstone fix could even deploy turned up a second,
independent problem. `vercel.json` excludes `data` from deploys (ISR cost
control, 2026-08-24 — correct and protected by the playbook), but **three files
under `data/` are static imports compiled into the bundle**:

| file | imported by | governs |
|---|---|---|
| `data/gsc-url-signals.json` | `lib/seo/gsc-signals.ts` | the thin-story **noindex** policy |
| `data/lost-stories.json` | `lib/news/story-resolution.ts` | tombstoned 404s vs 500s |
| `data/benchmark-history.json` | `app/admin/status/page.tsx` | admin display only |

`scripts/gsc-report.mjs` writes nothing outside `data/`, so the weekly GSC
commit **never deploys**. Verified by running the real ignoreCommand against
the last three gsc-bot commits — `520caef`, `30ed70f`, `e9f6a36` — all exit
`0 = skip`. `lib/seo/gsc-signals.ts` asserted the opposite in a comment ("the
weekly commit triggers a deploy and every page sees the same report"); that
comment is now corrected in the file itself.

It fails safe rather than dangerously: a deployed signals report past 14 days
counts as *no data* and the policy then noindexes nothing, so the thin-story
policy is mostly **inert** rather than wrong. That does reconcile a loose end in
backlog item 0b — the 33-URL sweep finding "33 of 33 serve `index, follow`" is
precisely what an inert policy looks like, so it was weaker evidence than it was
read as. The `lost-stories.json` case is sharper: a tombstone commit touching
only `data/` would silently never take effect, and today's worked only because
it also touched `tests/`.

**Filed with the exact fix (AND a second `git diff --quiet` over those three
files onto the ignoreCommand) but deliberately not shipped today** — deploys are
already failing, and changing deploy config mid-incident adds a second variable.
