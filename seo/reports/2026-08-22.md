## 4. The finding

Probing the whole sitemap: **2 of 743** URLs 404, and — the part that matters
— **2 of the 40 newest**, the entries Google News fetches within minutes of
publication.

What the evidence said, in the order it arrived:

- Both 404s served `x-vercel-cache: HIT` with a rising `age`. Cached, not live.
- `/story/<id-token>` for the same clusters answered **307 pointing at the very
  slug that was 404ing**. The cluster was live, under that exact slug. Only
  the cached answer was wrong.
- The first pair I found answered **200** a few minutes later, once the ISR
  entry expired. Self-healing, and therefore invisible to any check that runs
  once a day.

Cause: `/news-sitemap.xml` is force-dynamic and advertises a cluster the moment
it enters the live dataset. Database writes have been batched to a ~25-30
minute cadence since 2026-08-21 (`lib/database/persist-gate.ts`, a Neon
compute-cost fix). So a story page rendering from a slightly older dataset
generation missed the live lookup **and** the archive, and answered 404 —
which ISR then stored for its full 300 s window.

This is a side effect of the cost-control batching. It did not exist while
writes were immediate, and it is not in any report before today.

## 5. What shipped — `f757bba`

`resolveStoryRequest` now answers `unavailable` (a retriable 5xx, which ISR
does not store) instead of 404 when the archive answers "no such story" about
a slug carrying a well-formed cluster-id token (`c` + 12 hex).

Two bounds keep the status code a diagnosis rather than a blanket:

- **Junk paths still 404.** No cluster-id token means we could never have
  published it, whatever the database says.
- **A deployment with no database still 404s.** It was never in the
  batched-write window and never promised permanence. This preserves the
  2026-08-21 decision that "no `DATABASE_URL`" and "database failing" must
  stay distinguishable from outside.

### One approach was built, tested, and thrown away

The first fix kept the 404 and made it uncacheable instead — `await
connection()` before `notFound()`, so the render leaves the ISR path. It
typechecked and built. Running it against the production build locally
returned **500** on every story 404 with `digest: DYNAMIC_SERVER_USAGE`: Next
16 will not let a segment that declares `revalidate` opt into dynamic
rendering per request. Caught before pushing because the local production
server was run, not because the build was clean — the build was clean.

### A test whose premise had expired

`tests/unit/archive-outage.test.ts` asserted the old behaviour in as many
words, with a comment explaining why it was right: *"The outage guard must not
turn every unknown story id into a 5xx once the database is healthy again."*
It was right — while writes were immediate. It was corrected in place with the
reason recorded, and two bound tests were added next to it (no-token slug,
no-archive deployment). Not weakened to get a green run.

### Also fixed: a pre-existing e2e failure on `main`

`tests/e2e/hubs.spec.ts` "/topics lists the hubs under Browse by topic" fails
on clean `main` — verified by stashing this run's changes and re-running. The
page now links its hubs from the footer as well, so the unscoped
`"Elections 2026"` locator matched twice and failed Playwright strict mode on
a page that is correct. Scoped to `<main>`.
