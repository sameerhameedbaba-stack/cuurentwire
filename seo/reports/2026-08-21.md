# SEO daily loop — 2026-08-21

Every number below comes from a fetch or command run during this session.
Site: https://currentwire.us. Three code commits to `main` (`d060817`,
`4e14f29`, `8278520`), deployed and verified live.

## Outcome

**The site was telling Google that 1,322 permanent story URLs were gone.** The
Neon story archive stopped answering some time after 2026-08-19 22:20 UTC, and
the site's response to that outage — not the outage itself — was the damage:
every archive read caught its own failure and returned empty, so "the database
is down" and "that story never existed" arrived at the HTTP layer as the same
value. The result was a hard **404** on 1,322 of 1,329 published `/story/`
URLs and a **200 with an empty urlset** on `/archive-sitemap.xml` — a valid,
cacheable claim of zero permanent story URLs where 2,793 were advertised the
day before. Both are permanent signals that outlive the outage.

That is fixed and verified live: **0 URLs now return 4xx**; they return a
retriable 5xx instead, and the archive sitemap returns 503 with `Retry-After`.
Health-check failures went **4 → 1**, and the one that remains is the outage
itself, reported with the five-minute owner action that ends it.

The outage is **not** fixed — nothing in this repository can fix it. See
"Needed from the owner".

## 3. What shipped

### The archive outage no longer emits permanent "gone" signals — `d060817`

Reads that decide *whether a URL exists* now throw `ArchiveUnavailableError`
instead of returning empty. Reads that merely *enrich* a page keep degrading
quietly — which is why live story pages were unaffected throughout.

| Surface | Before | After (verified live) |
|---|---|---|
| `/archive-sitemap.xml` | `200` + empty urlset, `max-age=3600` | **`503`** + `Retry-After: 3600` + `no-store` |
| Published `/story/` URL | **404** on 1,322 of 1,329 | **`500`**, retriable |
| `/story/<junk>` | 404 | 404, unchanged |
| Garbage non-story URL | 404 | 404, unchanged |
| Live `/story/` URL | 200 | 200, unchanged |
| `/archive` | 200 | 200, unchanged |

Three decisions worth keeping:

- **"No `DATABASE_URL`" is deliberately not this error.** A deployment that
  never promised permanence should still 404. That makes the status code a
  *diagnosis*, and the deploy answered a question nobody could answer from
  outside: production flipped to **503**, which proves `DATABASE_URL` is set
  and the database itself is failing. It narrows the owner's check from
  "Vercel or Neon?" to "Neon".
- **Junk paths still 404 mid-outage.** A slug with no well-formed cluster-id
  token (`c` + 12 hex — 1,660 of 1,660 ledger URLs match) was never a story URL
  whatever the database says.
- **`getArchiveBrowse` deliberately does not throw.** The first version made it
  throw too; `/archive` is prerendered at build time, so that would have failed
  `next build` exactly when the database is down — when the deploy carrying the
  fix has to succeed. Caught by reading the build's route table before pushing.

Verified against the production build locally with an unreachable
`DATABASE_URL` **before** pushing — a dead port is a perfectly good broken
database — then live after deploy. Guards: `tests/unit/archive-outage.test.ts`,
12 tests. One existing test asserted the old behaviour in as many words
("swallows query failures and returns null"); its premise was corrected in
place with the reason recorded, not weakened.

### `url-survival` must not call a 5xx a lost URL — `8278520`

The probe defends "a published URL never 404s". With every rotated-out story
answering 5xx it called them all "no longer resolve", which would have kept it
red for the whole outage and buried a real 404 regression under 1,555 lines of
expected noise. `GONE` (4xx) and `UNAVAILABLE` (5xx) are counted separately now.

| Probe run | Result |
|---|---|
| Session start (before fix) | **1,322 dead — all 404** |
| After deploy | **`GONE=0` `UNAVAILABLE=1555` `ok=350` `redirects=15`** |

### BBC PNGs routed through the `news` recipe — `4e14f29`

The last health-check failure was one **683 KB** BBC image, more than the rest
of `/top-100` put together. Measured live at width 976 on 10 assets, on bytes
**and** decoded pixels:

| Source format | `ace/standard` | `news` | Verdict |
|---|---|---|---|
| `.png` (6 of 6) | 140–929 KB, PNG | 28–106 KB, re-encoded JPEG, identical pixels | **−80% to −92%** |
| `.jpg` (4 of 4) | 39–137 KB | 45–157 KB | **+14% to +19% — worse** |

So the swap is PNG-only; a blanket switch would have been a ~15% regression on
the JPEGs that are most of BBC's feed images. Verified live after the next
ingest cycle: the same asset went **699,730 → 58,325 bytes at an unchanged
976x547**, and `publisher image weight` went from failing to
**`15 images, 1026 KB total, median 63 KB, max 144 KB`**.
