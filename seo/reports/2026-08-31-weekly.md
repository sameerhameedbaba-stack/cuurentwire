### 1. The coherence alert was failing on the site's own cost controls

`[auto-alert]` #2 has been red every night since 2026-08-23. Today's first run
reported **16 violations** — and every one of them was an `archive-vs-live`
disagreement whose own cause label said *staleness* or *skew*, not *resolution*:

```
violations: 16  ->  list-side staleness 14, story-side staleness 1, skew 1
                    resolution: 0
```

Those are not defects. `/[category]` carries `revalidate = 3600`, and the cron
deliberately does **not** revalidate the dynamic category pattern — that nuke is
what blew the Hobby tier on 2026-08-24, and the playbook protects its absence as
a hard constraint. Measured directly rather than assumed: `/business` answered
**`Age: 3020`**, inside its own 3,600 s window, while carrying two of the flagged
clusters. The probe was failing the build for the site working as designed, and
burying the one class that is a real bug.

`scripts/surface-coherence.mjs` now fails **only** on a same-generation
disagreement, and reports the rest as findings counted by cause. The guard
against this becoming a silent pass is a stamp-coverage check in the same idiom
the file already uses for card extraction: if the `cw-live-dataset-version`
regex ever rots, every disagreement would classify as "unknown", land in
findings, and the probe would pass forever while blind — so archive renders
carrying the stamp below `MIN_COVERAGE` now fail as `extraction-blind`.
Measured today: **16 of 16 carried it.**

**The payoff, on the re-run:** `violations=1 findings=4`, and the survivor is a
genuine defect that 16 non-defects had been hiding — a **category flap** on
cluster `c31fffb88ca32`, alternating `business` → `politics` → `business` →
`politics` across four dataset generations. Issue #2 therefore stays open, and
is now open for a real reason. That flap is filed as a backlog item; the
playbook's rule that classifier defects are engineered upstream with benchmark
coverage means it is not a same-run fix.

### 2. The homepage was loading three full-size off-screen images eagerly

Measured, then root-caused in the markup. On a 412×823 mobile viewport under
Lighthouse's mobile throttle, `/` marked **four** images eager. One is the hero,
correctly `fetchPriority="high"` and the only image allowlisted through the
optimizer. The other three are the "More top stories" rail — and they render at
**y = 1203 / 1319 / 1435**, more than a viewport below the fold, as **raw
publisher originals** (976×549, 1024×683) because only the hero is optimized:

```
LCP element  /_next/image?...&w=1080&q=75   loadTime 11,353 ms   renderTime 13,876 ms
requests 33  images 6  declared image bytes 592,537
```

`EAGER_THUMBNAILS = 3` in `TopStoriesSection.tsx` is correct for the `lg:` grid,
where the rail sits *beside* the hero and is genuinely above the fold. At
`grid-cols-1` it stacks below it. Google scores the mobile viewport.

The fix keeps the reason the eager rail was added — the comment records that an
imageless hero would otherwise leave the page with no protected LCP candidate —
and pays for it only in that case: `eagerThumbnails = hero.imageUrl ? 0 : 3`.
Guarded by a new Playwright test asserting that when the hero has an image,
exactly one image is `fetchpriority="high"` and exactly one is eager.

**Verified live after deploy — and it did NOT fix LCP. Read this before
building on it.** The change works and does what it says: the homepage now
marks **1 image eager, 1 high-priority** (was 4 and 1), and the critical path
dropped from **6 image requests / 592,537 bytes to 5 / 437,713**. But three
post-deploy runs measured `/` at LCP **14,060 / 13,208 / 12,664 ms** — no
better than the 11,472 / 10,164 before it, and inside the same wide variance
band. So the images were a real inefficiency and **not the bottleneck**, and
this report's original framing of them as "the LCP budget" was wrong.

**What the bottleneck actually is, measured on the same runs:**

```
responseStart        120 ms    server is fast
responseEnd          410 ms    all 338 KB of HTML delivered
domInteractive     9,684 ms    <- 9.3 s of main-thread work, bytes already in hand
domContentLoaded   9,684 ms
loadEvent         14,649 ms
decodedBodySize  343,029 bytes
```

FCP came in at **9,332–11,944 ms** and LCP tracks it almost exactly, so nothing
paints for nine to twelve seconds. The network and the server are done at
410 ms. This is **main-thread cost — parsing 343 KB of HTML and hydrating a
large React tree under a 4× CPU throttle** — not image loading, not TTFB, and
not something a `loading` attribute can reach. The largest single script is
Google Analytics' `gtag.js` at **173,356 bytes**, which is the only script with
a reported content-length; the Next chunks report zero and were not
individually sized this run.

That is as far as the evidence goes. The fix is kept because fewer off-screen
full-size downloads is right regardless, and it is now guarded — but the
performance work that matters is payload and hydration cost, and it is next
week's item 2, re-aimed.

serves a 2.4 MB `archive-sitemap.xml` that grows every day, three sitemaps, RSS
and 11 category feeds, plus a per-story Satori OG render. Whatever the exact
split, non-HTML fetching is consuming the budget that is not reaching the pages
that need indexing. This is worth a dedicated measurement next run — and it
gives the long-deferred `s-maxage` on sitemap/RSS responses (backlog item 0b,
"secondary levers") a real justification instead of a theoretical one.

**3. Desktop 92% against Smartphone 3%.** Google indexes mobile-first, so a
crawl this desktop-skewed is worth understanding rather than assuming benign.
Recorded, not diagnosed — one reading is not a trend.

**Crawl health itself is good:** 200s at 99%, 5xx under 1%, 162 ms average
