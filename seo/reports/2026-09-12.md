## 1. The top of the board: instrumented, and the surface is now measured

The 09-10 run closed the symptom (four URLs tombstoned) and left the cause
open, naming the next step: *"nothing today records when a cluster enters the
news sitemap versus when its archive row is written."* That is what shipped.

### What the measurement found before a line of the instrument was written

All 760 story ids advertised in either sitemap, checked against
`/api/stats/archive-sources`, **2026-09-11 22:28 UTC**:

| Surface | Advertised | No archive row |
|---|---|---|
| `news-sitemap.xml` | 739 | **0** |
| `sitemap.xml` | 200 | **19** |

Only one of the two sitemaps can advertise an unarchived story, and it is not
the one anyone was watching:

- **`news-sitemap.xml` is gated on archive standing** (2515c55, 2026-08-24), so
  by construction it cannot carry one — and measured, it does not.
- **`sitemap.xml` is not gated.** `app/sitemap.ts` is `force-dynamic` over
  `dataset.clusters.slice(0, 200)` — the **live** dataset.

### The 19 are not a defect, and here is the proof

Every one was **0.0–0.3 h old** (`lastmod` 22:00–22:51 UTC) and every one
served:

```
slug=200  byid=307   ×19
--- controls ---     home=200   live story=200
```

That is the normal batched-write window: `PERSIST_MIN_INTERVAL_MS` is 25 min
and the cold window reaches minute 15 of each 30
(`lib/database/persist-gate.ts`), so a brand-new story is *expected* to be
advertised before it is archived.

**Re-measured seven minutes later, 22:35:29 UTC:**

```
Sitemap-to-archive gap — 2026-09-11T22:35:29.496Z
  advertised story URLs : 760
  with an archive row   : 760
  pending (< 90m)    : 0
  OVERDUE (> 90m)    : 0
    news-sitemap.xml: 739 advertised, 0 unarchived
    sitemap.xml: 200 advertised, 0 unarchived
```

The persist burst landed between the two readings and wrote all 19. **That is
the gap opening and closing, observed directly** — the first time this repo has
watched it happen rather than inferred it.

### What shipped — `53bf6ad`

`scripts/sitemap-archive-gap.mjs` + `scripts/sitemap-archive-gap-lib.mjs`,
classifying every advertised story as **archived** / **pending** (inside the
window) / **overdue** (no row, older than a 90-minute grace = twice the ~45 min
worst-case persist delay). An overdue entry is an orphan candidate: a URL on
its way to a permanent 500, because if it leaves the live dataset it is then
neither live nor archived and `story-resolution`'s unavailable shield has no
clock.

**It is an instrument, not a gate** — the same discipline as
`general-orphan-rate.mjs`. A high overdue count never fails the run; `exit 1`
means the corpus could not be **measured**. A non-200 from `archive-sources`
aborts rather than reporting the entire corpus as orphaned during an archive
outage — the false alarm that would otherwise fire on the worst possible day.

**24 unit tests.** The boundary this rests on is persist-gate's cadence, so one
test derives the worst case from `PERSIST_MIN_INTERVAL_MS` itself and fails if
`GRACE_MS` ever stops being twice it — if the write cadence is widened, the
threshold gets re-derived instead of silently reclassifying normal batching as
orphan candidates.

**Negative control before commit:** shrinking `GRACE_MS` to 30 min and making an
undated entry `overdue` failed **exactly** those two tests and no others —
`expected 1800000 to be greater than or equal to 4800000` and
`expected 1 to be +0`.

Gates, all green before push: `npx vitest run` **1076 passed / 3 skipped**,
`npx tsc --noEmit` clean, `npx eslint app lib components config scripts tests`
0 errors (1 pre-existing warning), `npx next build` succeeded. Playwright not
run — no template changed.

### What this does NOT settle

It settles **where** an advertised-but-never-archived URL can come from:
`sitemap.xml`, during the persist window — which is also a surface
`url-survival.mjs` reads, consistent with how the four 09-09 orphans entered
`data/url-ledger.json` with `lastOk: null`.

It does **not** establish that a cluster leaving the live dataset before its
burst is what happened on 09-09. That remains unmeasured, and it is precisely
what the `overdue` bucket exists to catch in the act. **No mechanism is being
published as a finding here** — this file has been burned by exactly that.

## 2. New defect: a green `gsc.yml` run that refreshed nothing

`data/gsc-daily.json` was **five days stale** at the start of this run
(`generatedAt 2026-09-07T13:39:11.445Z`) — despite the 09-10 run dispatching
`gsc.yml` for exactly this reason. That dispatch, **run #15** (2026-09-09 22:24
UTC), reports **every step green** and produced **no commit at all**.

Measured:

- All seven `data/gsc-*.json` files sat at `generatedAt 2026-09-07T13:39:11.445Z`.
- `gsc-report.json` writes that field **unconditionally** at the end of
  `main()`, so a run that completes always produces a diff. This one did not.
- **Not the secret.** `gsc-crawl-freshness.yml` authenticates with the same
  `GSC_SERVICE_ACCOUNT_JSON` and reached Search Console at 2026-09-11 12:53 UTC.
- **Not a broken workflow.** Re-dispatched this run as a live test:
  **run #16 committed fresh data normally** (`29e9320`). So it is intermittent.

**Mechanism unproven** — the run logs need an authenticated `gh` and the local
token is invalid (`The token in default is invalid`). Filed, not fixed, and not
guessed at.

The durable point is the class, and it is the standing order's rule 2 almost
word for word: **this workflow has no way to say "I refreshed nothing"**, and a
green run was taken as fresh data by the run that dispatched it. The loop only
caught it by comparing `generatedAt` to the calendar. The fix is a freshness
assertion in the workflow — the same shape as item 0c. **Next run's candidate.**
