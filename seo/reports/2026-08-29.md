## 2. Shipped — `a0d26f0`: the revalidation window rotates, so every live story stays fresh

**The defect, found by comparing two numbers that had never been compared.**
`app/api/cron/news-refresh/route.ts` marked `dataset.clusters.slice(0, 150)`
for re-render on each burst — always the same top 150 by ranking score. The
live dataset holds **726 clusters**, measured this run on
`/api/stats/coverage`. So **576 live story pages (79%) were never marked at
all.** Nothing else reaches them: the story route carries a 30-day ISR TTL
(item 0b), and a page rendered from the archive performs no tagged read, so
`revalidateTag(NEWS_CACHE_TAG)` misses it too. A page that rendered from the
archive before its cluster entered the live snapshot kept serving that
archived copy — `dateModified` frozen, `isBasedOn` under-reporting every
publication that picked the story up later — on the site's only indexed,
click-earning surface.

**The fix does not spend more; it spends better.** `selectRevalidationSlugs`
(`lib/news/revalidation-window.ts`) keeps the bound at **150 marks per burst
— the billed quantity is unchanged**, which the playbook's ISR-cost
constraint requires after the 2026-08-24 Hobby-tier outage — and splits it
into a fixed head of 100 (what readers and Google News see) plus a rotating
50-URL slice of the tail. The cursor comes from the clock, so the serverless
cron stays stateless. Every live story is re-rendered within **13 bursts ≈
6.5 hours** at the measured ~2 bursts/hour, against never before.

Nine unit tests pin both halves (`tests/unit/revalidation-window.test.ts`):
the per-burst count never exceeds the old bound, the head is always marked,
and sweeping a full cycle covers all 726 exactly once.

**Gates before push:** 946 unit tests passed (3 skipped), `tsc --noEmit`
clean, `eslint .` clean (2 pre-existing warnings), `npm run build` clean,
**111 Playwright tests passed** on the first run — no control run needed.

## 3. The diagnostic that shipped with it, and how it corrected this run

The story page already computed the live snapshot version it consulted before
falling back to the archive, then **threw it away**. That is precisely why
`[auto-alert]` #2 had been unreadable for six days: a page stamped
`archive:…` while list surfaces showed the cluster live, and nothing said
whether the page had missed a cluster the current generation held (a
resolution bug) or was an old render (a freshness bug). Archive-rendered
pages now stamp `cw-live-dataset-version`, and `surface-coherence.mjs`
labels every `archive-vs-live` violation with its cause.

**It overturned my own diagnosis within minutes of deploying.** Both
clusters that violated before the fix stamped
`cw-live-dataset-version: 20260828T221542Z-d00266` afterwards — and **neither
cluster is in the live dataset any more**, verified two independent ways:
absent from force-dynamic `/latest` at that same generation, and absent from
a freshly prerendered `/` (`20260828T222628Z`, `Age: 0`). Those two story
pages were **correct**; the cached **list** pages were the stale side. Since
surfaces legitimately read dataset entries up to ~29 minutes apart (the
1,740 s floor in `lib/cache/store.ts`), a cross-generation disagreement is
skew — only a **same-generation** disagreement is a bug. The probe now says
which of the three it is, so no future run re-derives this.

**Post-fix re-run against production, 22:28 UTC — violations 2 → 1:**

```
VIOLATION c92e8ee37fe9e   storyVersion  archive:2026-08-28T12:31:08Z
  liveVersionAtRender 20260828T221542Z-d00266     listSurfaces /business (r1,r2)
  cause "story-side staleness: an older render, healed by the rotating
         revalidation window"
```

That is exactly the class the rotation fixes. It heals within one rotation
cycle (~6.5 h), which is longer than this run, so **`[auto-alert]` #2 is not
being closed on this write-up** — it should be judged on the next scheduled
coherence run, and judged on the `cause` label rather than the violation
count, because list-side skew will keep producing violations that are
nobody's bug.

## 4. Refuted this run — the meta-description "standfirst junction", do not rebuild it

Backlog item 5 recorded a root cause for the 43% of story meta descriptions
that end mid-sentence: an RSS standfirst concatenated to the body with no
punctuation, so the sentence splitter finds no boundary. **The mechanism is
real and I found it in the code** — `stripHtml` deliberately turns block
boundaries into newlines, `cleanDescription` splits on them, and then
`kept.join(" ")` (`lib/news/normalization/boilerplate.ts:234`) destroys them
again before `metaDescription` ever sees the text.

**Then I measured it, and it is not the driver.** A boundary-preserving join
was implemented and run over real feed data pulled this run — 24 curated
feeds, **268 descriptions** through the actual pipeline (`parseItems` →
`normalizeArticle` → `metaDescription`):

| | descriptions | over 155 chars | clipped mid-sentence |
|---|---|---|---|
| current | 268 | 113 | **52** |
| boundary-preserving join | 268 | 113 | **51** |

One description in 268. The clipped cases are overwhelmingly **genuine single
sentences longer than 155 characters** (NPR house style dominated the
sample). The change was reverted unshipped and the finding written into
BACKLOG item 5, which is downgraded: its description half is not a CTR defect
worth engineering. Its title half (85% over 60 chars) is untouched and keeps
its rank.
