## 2. Shipped: a monitor that watches Google instead of us — item 0c

`1c8e098` — `.github/workflows/gsc-crawl-freshness.yml`, daily at 08:25 UTC.

Every probe this repo owns — `seo-health`, `uptime`, `url-survival`,
`surface-coherence` — measures what the site **serves**, and all four were
green every single day through a two-week crawl blackout. Search Console's
`sitemaps.list` carries the one field none of them can see: when Google last
*downloaded* each sitemap. The job fails past 72 h, opens one `[auto-alert]`
issue (issue creation emails the owner) and closes it on the next green run.

**Not a step in `gsc.yml`, against that file's own instruction**, and the
reason is arithmetic: `gsc.yml` runs weekly, so a 72-hour threshold checked
there is not a 72-hour threshold. Standing alone costs one OAuth token and one
GET per day — no `npm install`, no file written, no commit, so no deploy.

**Verified live, end to end.** Not "the workflow is green" (it is red, and
correctly so) and not "the script runs locally". The run authenticated to the
real property, read real data, judged it, and opened
[issue #11](https://github.com/sameerhameedbaba-stack/cuurentwire/issues/11)
containing the three measured ages above. **That alert is true and will stay
open until Googlebot comes back. It is not noise and must not be muted.**

**The boundary this change moved, and the test that now holds it.** GitHub
auto-disables scheduled workflows after 60 days of repo inactivity, so
`url-survival.yml` and `surface-coherence.yml` each re-enable the whole
scheduled set — a gap found by hand on 2026-09-04, when the list covered 3 of
9. A tenth workflow makes both lists incomplete *silently*. Both lists were
updated and `tests/unit/gsc-crawl-freshness.test.ts` now derives the scheduled
set from `.github/workflows/` and asserts both lists equal it. Run as a
negative control before the fix: it failed on exactly those two assertions.

Twelve tests total; the evaluator's boundary is pinned at exactly 72 h, a
just-submitted-and-not-yet-read sitemap does not alarm, and an unparseable
timestamp reports `unknown` rather than stale.

**The half of 0c that cannot be built, with the evidence.** "Indexed pages
down >10% week over week" needs the Page-indexing count, which no Search
Console API exposes — there is no Index-Coverage endpoint, and the
`contents[].indexed` field on `sitemaps.list` is the deprecated one that
returns 0. The nearest live signal is the existing 34-URL evergreen sample in
`data/gsc-indexation.json`. That is a sample of evergreen surfaces, not the
indexed count, and turning it into an alarm is refiled as **0c-ii** rather
than quietly dropped or quietly mislabelled.

## 3. Shipped: an incident that is still happening now keeps explaining the dip

`0c6e8f6` — `data/incidents.json` is the file that stops a future run
re-investigating a cause the loop already knows. The crawl collapse was
measured three ways on 09-07 and **was never written to it**.

Adding it exposed a defect in the mechanism: `buildDailySeries` annotates
`[date, end]`, so an incident with no end yet marks exactly **one day**. The
collapse would have annotated 2026-08-21 and nothing else, `explained` would
have gone false within a week, and some later run would have spent itself
re-deriving a known cause. `ongoing: true` now annotates from the start until
an `end` closes it. Closed incidents are unchanged and asserted by a second
test; the new test was run against the old predicate first and failed alone.

## 4. Corrected: the archive sitemap count went DOWN

Measured live 22:12 UTC: **17,426** URLs, against **17,716** at 12:41 UTC the
same day — **−290 in 9.5 hours**, the first decline in the series. Confirmed
by two fetches (`X-Vercel-Cache: HIT`, age 285 s, so inside the hour) and by
`seo-health.mjs` independently reporting the same 17,426.

This is not a leak and not an outage. `app/archive-sitemap.xml/route.ts` lists
non-merged stories the thin-story policy keeps indexable, and that predicate
carries a **rolling 336-hour term**: a single-source story with no history and
no Search Console signal leaves the sitemap fourteen days after it is first
seen, and a merge removes one permanently.

Ruled out first: the protected-id list is **516 in all three of the last GSC
report commits** (`471221b`, `f988b70`, `7f341e3`), so today's report rewrite
did not shrink the set.

**So the count rises and falls by design, and no runway date can be derived by
differencing it — at any window size.** Both dates this project has published
(the `2026-09-21` once written into `seo-health.mjs`, and the `2026-09-24` in
the run brief) were that mistake at different scales, and so was the careful
206/day, ~132-day version written yesterday. The comment in `seo-health.mjs`
now carries the reading and the mechanism. The `fail()` itself asserts on the
**count**, which was correct all three times the comment above it was wrong.
Sharding stays additive-first and is not urgent.

Memory note: `seo/MEMORY/2026-09-08-a-count-can-go-down.md`.
