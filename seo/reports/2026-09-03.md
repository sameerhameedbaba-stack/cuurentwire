## 3d. The actual root cause, and why it could never self-heal

```
03:50:10.626  Cloning github.com/sameerhameedbaba-stack/cuurentwire (Commit: 8f4d087)
03:50:11.523  Cloning completed: 897.000ms
03:50:12.266  Restored build cache from previous deployment
03:50:13.596  Running "git diff --quiet ${VERCEL_GIT_PREVIOUS_SHA:-HEAD^} HEAD -- . …"
03:50:13.653  fatal: bad object f8805af4282c6a4405daca6b8961ea5ae092b42e
```

`VERCEL_GIT_PREVIOUS_SHA` is the commit of the last **successful** deployment,
and Vercel builds from a **shallow clone**. The ignored-build step's contract is
`exit 0` = skip, `exit 1` = build, **anything else = build failure**. Reproduced
locally in a throwaway repo: the old inline command exits **128** on a base sha
it does not have.

The deadlock is the part worth understanding, because it is why three days of
pushes made it worse rather than better:

```
f8805af deploys OK  ->  VERCEL_GIT_PREVIOUS_SHA = f8805af
72e30e7 pushed      ->  diff vs f8805af … still in the clone? apparently not -> exit 128 -> FAIL
                    ->  last success is STILL f8805af
next commit         ->  diff vs f8805af, now further back in history -> FAIL
…                       every push moves f8805af further out of reach
```

It cannot recover on its own, and every additional commit deepens it.

**The fix** moves the logic to `scripts/vercel-ignore-build.sh`, which verifies
the base commit is actually in the clone (`git cat-file -e`) before diffing and
**can only ever exit 0 or 1** — when it cannot answer the question it builds,
because a needless build costs ISR writes while a crashed one costs shipping
entirely. The skip rule is unchanged: still no build for commits touching only
`seo/`, `docs/`, `data/`, `.github/` and top-level `*.md` (the 2026-08-24 ISR
cost control).

Guarded by `tests/unit/vercel-ignore-build.test.ts` — 6 cases driven in a real
throwaway git repo the way Vercel drives it, including the missing-base-sha case
that caused this and a case asserting the script can never return a code Vercel
would read as an error.

**Both halves verified live:** `94c7246` built in **34 s** and is serving
Production; the two `.github`-only commits pushed after it produced **no failed
deployment**, so the skip path works too.

## 4. Shipped: `deploy-watch.yml` — verified live in CI (`68d33b2`)

The check whose absence made a 3-day shipping outage invisible. It needs
**nothing from the site** — no `/api/version`, no build stamp — which is the
whole point: it has to work *while* deploys are broken.

Two rules, because the first has a blind spot:

1. a failed deployment standing with no success after it → not shipping;
2. a HEAD commit older than 2 h with **no deployment record at all** → also not
   shipping. Without rule 2, disconnecting the integration would freeze the
   newest record at `success` forever and the check would go permanently green.

**Exit 1 (not shipping) and exit 2 (could not read the API) are kept distinct,
and only exit 1 opens the alert issue.** A rate limit is not evidence of an
outage and must never page the owner as one — a lesson this run learned the
direct way, by exhausting the anonymous 60 req/h budget mid-investigation.

**Live evidence, on GitHub's infrastructure, not locally:**

```
workflow run  Deploy watch  -> failed (the correct verdict)
issue #8      [auto-alert] production is not shipping pushed code   OPENED
              body: "…did NOT reach production… merged fixes are not live…
                     Vercel -> CurrentWire -> Deployments -> newest failed one"
```

Verified before push against a stub replaying this run's **real recorded API
shapes**: outage → exit 1 naming the stranded commits with `f8805af` as last
success; healthy → exit 0; dead endpoint → exit 2; preview deployments ignored.
15 unit cases in `tests/unit/deploy-watch-lib.test.ts`.

One implementation note worth keeping: `process.exit()` with undici sockets open
aborts Node on Windows with a libuv assertion and reports **127**, which would
have made every real verdict unreadable from this machine. The script sets
`process.exitCode` instead.

## 5. Shipped and LIVE: the newsletter form was blocked by our own CSP (`d3f8128`)

Found by reading production's response headers, not by any test. The sitewide
policy said `form-action 'self'`, while `components/layout/NewsletterSignup.tsx`
posts to `https://buttondown.com/api/emails/embed-subscribe/currentwire`.

**A browser blocks a cross-origin form submission that `form-action` does not
name, and logs nothing server-side.** The footer signup would have subscribed
**nobody**, silently, from the moment it went live — on a feature whose entire
purpose is collecting addresses, and against a Buttondown account currently in
new-sender review. It has never run in a browser, because it has never shipped.

The policy moves to `config/csp.ts` so it can be tested at all. The guard does
not assert a string: it **reads the form's own `action` attribute out of the
component** and requires the policy to name that origin, so changing providers
cannot silently re-open the hole. Proved by restoring `form-action 'self'` and
watching it fail.

Verified first on a local production build, then — after the deploy fix landed
— **on production itself**: `form-action 'self' https://buttondown.com` in the
served header, and the form rendering with its Buttondown action. The form and
the policy that permits its POST went live in the same deploy, which is the only
reason the signup works at all rather than failing silently.
