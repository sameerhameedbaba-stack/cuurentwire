**The boundary this moves is the length ceiling, so it ships with the test
that holds it** (rule 4). `tests/unit/meta-description-length.test.ts` asserts
every hub description and every page-level `DESCRIPTION` literal is ≤ 160,
plus a guard that the source scan actually matched something — a regex that
silently stopped matching would otherwise turn the whole test into a no-op.
**Negative control run before committing:** padding one hub description makes
the test fail, so the guard can actually fail.

## 6. Archive sitemap runway — the number in the code is measuring the wrong thing

Re-measured live: **17,366** permanent story URLs (independently by
`grep -c` and by `seo-health`), against `ARCHIVE_SHARD_AT = 45_000` — 27,634
left.

The comment in `scripts/seo-health.mjs` says ~1,620/day and puts the `fail()`
at about 2026-09-21. That rate is read off **per-day `<lastmod>` counts**, and
today's data shows it cannot be a net-growth rate:

- per-day `<lastmod>` for Sep 1/2/3/4: 1,607 / 1,614 / 1,668 / **1,486**
- but the sitemap **total** went 16,973 (live, 09-03 22:05 UTC) → **17,366**
  (live, 09-04 21:55 UTC): net **+393**.

A `lastmod` is a modification date. 1,486 rows stamped with today's date over
a day that added 393 URLs means the figure counts re-modified (and possibly
tombstoned) rows, not new ones.

Runway therefore depends entirely on the window: **~70 days at 393/day**
(last 24 h), **~26 days at 1,081/day** (the 09-02 → 09-05 average, 3,242 over
3 days), ~17 days at the 1,620/day currently written into the code.

**Deliberately not rewriting that comment today.** One clean 24-hour delta is
exactly the sample size that produced the wrong number the first time, and
this repo already keeps a memory note about an unverified estimate written
into code as fact. What the next runs owe: record the archive-sitemap TOTAL
every run and re-derive the rate from totals only. **The additive shard routes
stay the plan and stay ahead of every one of these dates** — nothing about
this finding delays them.
