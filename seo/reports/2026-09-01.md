## 4. What shipped — `53ad4b1`

### The failure

`node scripts/seo-health.mjs` against production, 22:09 UTC:

```
FAIL news-sitemap URLs: 1/707 not directly 200
  e.g. …-c9e0f30ebe2a1 (1 redirect(s) -> …-c343d2e6168bf
       (different story id — a merged or non-canonical URL is advertised))
```

The check had already done the hard part before failing: it re-fetched to rule
out a rename race, then asked `/api/stats/archive-sources` which cluster is
merged. The answer **inverted the obvious reading**:

```
c9e0f30ebe2a1  merged = false   <- the advertised URL: the SURVIVOR
c343d2e6168bf  merged = true    <- its redirect target: merged away
```

So `/news-sitemap.xml` was advertising the correct canonical URL, and the
**story route** was 308-redirecting that survivor to the duplicate. Three URLs
of one story, measured within ten minutes of each other, all cache `HIT`s:

```
/story/<slug>-c9e0f30ebe2a1   308 -> …-c343d2e6168bf   (archive: merged=false)
/story/<slug>-c343d2e6168bf   200                      (archive: merged=true)
/story/c9e0f30ebe2a1          307 -> <slug>-c9e0f30ebe2a1
```

### Root cause

`findArchivedStory` was `cachedRead` keyed by the **raw lookup string**, so one
`story_archive` row was cached once per alias — canonical slug, bare cluster
id, and every retired slug a rename leaves behind — each entry with its own
independent 6-hour `ARCHIVE_ROW_TTL_S`. When `merged_into_cluster_id` flips,
entries filled before the flip keep serving the old direction, and nothing
reconciles them because **neither is stale in its own key's terms**. TTL
tuning, `revalidateTag` and ISR settings are all powerless against this: they
answer *when does this refresh*, and the defect is *how many of this are
there*.

This is the worst feed for it to land on. Googlebot-News fetches
`/news-sitemap.xml` within minutes of publication and follows what it
advertises, so a fresh story's canonical URL was handing the News crawler a
permanent redirect to a duplicate.

### The fix

`archiveRowCacheKey()` normalises the lookup to the story's cluster-id token —
every published slug ends with its own id (`CLUSTER_ID_RE`, verified against
all 1,660 ledger URLs) — so all aliases share one entry and cannot disagree. A
slug carrying no well-formed id token keeps its own key and the previous
behaviour. It **removes** reads rather than adding them, so it is free against
the ISR/database cost controls the playbook protects; no TTL moved.

9 new unit tests (`archiveRowCacheKey` identity/collision/junk/idempotence, and
alias consistency through a mocked db).

## 5. Found but deliberately not fixed

The now-passing health run surfaced the **opposite half of the same family**,
as a tolerated note rather than a failure:

```
note merge lag: …-c10f7079a8181 — the archive marks this cluster merged;
the news-sitemap gate reads standing through a 30-minute cache
```

`getNewsSitemapArchiveStatus` shares the `readFirstSeenEntries` cache entry
(`FIRST_SEEN_TTL_S = 1800`), keyed by the **sorted live cluster-id set**. That
key's own comment argues the staleness is harmless because "any dataset change
alters the id set" — but a merge flips `merged_into_cluster_id` on an existing
row *without* changing the live id set, so a stale `merged: false` can be
served for up to 30 minutes. Today's rate is **1 of 692**, which may not
justify the change on its own, so it is filed in `BACKLOG.md` with a costed
candidate fix and a note to measure the rate over a few runs first.
